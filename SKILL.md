# BPMN Diagramming

Профессионально моделируй **любой бизнес-процесс** в BPMN 2.0: от первичного интервью и разбора исходной схемы до логической проверки, корректной разводки стрелок и выдачи полного набора редактируемых, векторных и растровых файлов.

Навык предназначен не только для «рисования». Он должен сначала понять бизнес-логику, затем выбрать правильную BPMN-семантику, только потом строить геометрию. Нельзя скрывать неопределенности: если отсутствие ответа влияет на Pool/Lane, Gateway, цикл возврата, обязательное согласование или тестирование — задай пользователю короткий наводящий вопрос.

## When to Use

Используй навык, когда пользователь просит:
- создать BPMN 2.0 диаграмму по тексту, регламенту, интервью, SOP, инструкции или описанию процесса;
- преобразовать flowchart/swimlane/Visio/draw.io/изображение в BPMN 2.0;
- исправить существующую BPMN-схему, не меняя остальную логику;
- проверить Pool/Lane, Gateway, стрелки, согласования, тесты, возвраты и владельцев задач;
- сформировать редактируемый `.bpmn` и презентационные форматы;
- подготовить краткое описание/доклад по схеме;
- выдать полный архив всех форматов.

## Core Principle

Работай в 4 слоя:

1. **Business logic** — кто, что, зачем и при каких условиях делает.
2. **BPMN semantics** — Pool, Lane, Task, Event, Gateway, Sequence Flow, Message Flow, Data Object.
3. **Geometry** — размещение и маршруты стрелок без двусмысленностей.
4. **Delivery** — экспорт, краткое описание, отчет проверки, ZIP.

Не переходи к следующему слою, если предыдущий содержит существенную неоднозначность.

## Quick Start

1. Прочитай `references/intake-questions.md` и задай только недостающие вопросы.
2. Сформируй `process-model.json` по `templates/process-model.schema.json`.
3. Проверь модель логически по `references/bpmn-rules.md`.
4. Выполни:

```bash
python ${HERMES_SKILL_DIR}/scripts/check_env.py
python ${HERMES_SKILL_DIR}/scripts/build_bpmn.py process-model.json --out ./bpmn-output
```

5. Открой `bpmn-output/validation-report.txt`.
6. Если статус не `PASS`, исправь модель/waypoints и перезапусти.
7. Визуально проверь SVG/PDF. Если доступен `vision_analyze`, используй его как дополнительный quality gate.
8. Верни пользователю ZIP + основные форматы + краткое описание процесса.

## Procedure

### 1. Собери контекст

Извлеки из сообщения/файла/изображения:
- название и цель процесса;
- старт и успешный конец;
- участников и их организационную принадлежность;
- основной Happy Path;
- решения и условия;
- возвраты и повторные проверки;
- документы/данные;
- согласования;
- виды тестирования/приемки;
- желаемый стиль и форматы.

### 2. Задай наводящие вопросы

Задавай вопросы только там, где ответ влияет на модель. Не спрашивай то, что уже дано.

Сначала максимум 3–6 критичных вопросов. После ответа — следующий короткий блок только при необходимости.

Обязательно выясни:
- внутренний это участник или внешний;
- кто принимает решение;
- что означает `Нет`;
- куда идет возврат;
- какие проверки после доработки повторяются;
- какие действия параллельны, а какие последовательны.

Используй `references/intake-questions.md`.

### 3. Определи BPMN-границы

- Внутренние подразделения одной организации → один Pool + Lanes.
- Независимый внешний участник → отдельный Pool.
- Внутри Pool → Sequence Flow.
- Между Pools → Message Flow.

Не используй Message Flow как декоративную передачу работы между отделами одной компании.

### 4. Построй семантическую модель

Именуй задачи **глагол + объект**:
- `Разработать ТЗ`
- `Проверить договор`
- `Согласовать бюджет`

Gateway — это вопрос/маршрутизация, а не работа:
- `Бюджет согласован?`
- `Заявка полная?`

Подробные критерии выноси в `notes`/Text Annotation, а не в ромб.

### 5. Зафиксируй process-model.json

Используй шаблон из `templates/process-model.schema.json`.

Рекомендуемая структура:
- `process`
- `pools[].lanes[]`
- `nodes[]`
- `flows[]`
- `data_objects[]`
- `annotations[]`
- `stages[]`
- `brief`
- `style`

Для сложной геометрии задавай `x`, `y`, `width`, `height` и `waypoints` явно.

### 6. Построй и проверь

Запусти:

```bash
python ${HERMES_SKILL_DIR}/scripts/build_bpmn.py process-model.json --out ./bpmn-output
```

Скрипт создает BPMN 2.0 XML с BPMN DI и все доступные форматы.

### 7. Исправляй только то, что нужно

Если пользователь просит локальную правку:
- сохрани остальные ID, задачи, позиции и логику;
- меняй только указанные nodes/flows/waypoints;
- после правки снова запускай полную проверку.

### 8. Обязательная проверка стрелок

Для каждого Sequence Flow:
- начало на границе исходного элемента;
- конец на границе целевого элемента;
- последний сегмент входит перпендикулярно;
- только горизонтальные/вертикальные сегменты;
- наконечник не находится внутри Task;
- линия не проходит сквозь чужой BPMN-элемент;
- линия не лежит поверх границы Lane;
- нет наложения с другим flow;
- `Да/Нет` привязаны к правильным исходящим веткам.

Подробнее: `references/arrow-layout-rules.md`.

### 9. Краткое описание схемы

Всегда сформируй `brief-description.md` и короткую версию в ответе пользователю.

По умолчанию 3–6 предложений:
1. цель процесса;
2. старт и основные этапы;
3. ключевые согласования/проверки;
4. циклы доработки;
5. финальный результат.

Не перегружай краткий доклад BPMN-терминами.

### 10. Полный пакет файлов

При доступных зависимостях создай:
- `process.bpmn`
- `process.xml`
- `process.svg`
- `process.pdf`
- `process.png`
- `process.jpg`
- `process.webp`
- `process.tiff`
- `process.eps`
- `process.html`
- `process-model.json`
- `brief-description.md`
- `validation-report.txt`
- `all-formats.zip`

EPS создавай только если доступен Inkscape. Если формат недоступен — честно укажи причину в validation report.

## Output Response Pattern

После успешной генерации:

1. Коротко сообщи, что диаграмма создана/исправлена и проверена.
2. Дай `all-formats.zip` первым.
3. Далее перечисли основные файлы по типам.
4. Приведи 3–6 предложений краткого описания схемы.
5. Укажи статус validation report.
6. Для высокодетализированных изображений добавь литеральную директиву:

`[[as_document]]`

Hermes использует ее для доставки изображения как файла без потери качества.

## Pitfalls

- Не рисуй обычный flowchart под видом BPMN.
- Не смешивай Lane и Pool.
- Не пропускай повторное согласование после доработки, если оно обязательно.
- Не объединяй разные проверки, если у них разные владельцы/цели.
- Не ставь Task на границу Lane.
- Не пускай Sequence Flow по границе Lane.
- Не используй пунктир для Sequence Flow.
- Не делай огромный общий возвратный «автобус», если конкретные циклы можно показать локально.
- Не ставь стрелочный наконечник внутрь блока.
- Не заявляй «OMG XSD validated», если официальная XSD реально не запускалась.

## Verification

Финальная выдача разрешена при статусе `PASS` в `validation-report.txt`.

Минимальные нули:
- broken references = 0
- off-boundary endpoints = 0
- diagonal Sequence Flow segments = 0
- non-perpendicular target entries = 0
- flows through unrelated BPMN nodes = 0
- overlapping collinear Sequence Flow segments = 0
- Tasks crossing Lane boundaries = 0

Структурный PASS не заменяет визуальный просмотр. Всегда проверь SVG/PDF на читаемость текста и визуальное слияние линий.
